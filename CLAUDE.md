# Project Guide for Claude

This file tells Claude Code how this codebase is structured and what conventions to follow. Read it before making changes.

## Stack

- **Build**: Vite + React 18 + TypeScript (strict)
- **Routing**: react-router-dom v6 (`src/routes/router.tsx`)
- **Server state**: TanStack Query (never store server data in Zustand)
- **Client state**: Zustand (`src/stores/`)
- **API layer**: generated by **orval** from the backend OpenAPI spec into `src/api/generated/` — DO NOT hand-edit generated files
- **HTTP**: axios via `src/api/axios-instance.ts` (auth + interceptors live here)
- **Dates**: `date-fns` + `date-fns-tz` via helpers in `src/utils/date.ts` — never use `new Date()` formatting directly in components
- **Utils**: `es-toolkit` (lodash replacement) — import from `es-toolkit`, not `lodash`
- **Hooks**: `ahooks` for common hooks before writing custom ones
- **Charts**: `recharts`
- **Drag & drop**: `@dnd-kit`
- **Calendar**: `@fullcalendar/react`
- **Signature**: `react-signature-canvas`
- **Downloads**: helpers in `src/utils/download.ts` (file-saver + jszip)

## Folder structure

```
src/
  api/            # axios instance + orval-generated services (generated/)
  components/
    common/       # shared, reusable presentational components
    layout/       # app shell, headers, sidebars
  config/         # app config, constants, env access
  features/       # feature-based modules (each owns its components/hooks/types)
  hooks/          # shared custom hooks
  lib/            # third-party setup (query client, etc.)
  pages/          # route-level page components
  routes/         # router definition
  services/       # business logic wrapping generated API calls
  stores/         # zustand stores
  styles/         # global css
  types/          # shared TypeScript types
  utils/          # pure helper functions
```

## Conventions

- **Path alias**: import via `@/...` (maps to `src/`), not relative `../../`.
- **Components**: function components, named exports. One component per file. PascalCase filenames.
- **API usage**: call generated TanStack Query hooks from orval. If business logic is needed, wrap them in `src/services/` — don't put fetch logic in components.
- **New feature**: create a folder under `src/features/<name>/` containing `components/`, `hooks/`, `types.ts`. Keep feature code colocated.
- **State decision**: server data → TanStack Query. UI/ephemeral/global client state → Zustand. Local state → `useState`.
- **Types**: prefer types generated in `src/api/generated/model`. Shared cross-feature types go in `src/types/`.
- **Formatting**: Prettier + ESLint enforced via pre-commit (lint-staged). Run `npm run lint:fix` and `npm run typecheck` before considering work done.

## Commands

- `npm run dev` — start dev server (port 3000)
- `npm run api:gen` — regenerate API layer from OpenAPI spec (after backend changes)
- `npm run typecheck` — strict TS check (run before finishing any task)
- `npm run lint:fix` — fix lint issues

## Definition of done (for any task Claude does)

1. Code follows the folder structure and conventions above.
2. `npm run typecheck` passes.
3. `npm run lint` passes.
4. No hand-edits to `src/api/generated/`.
5. Server state uses TanStack Query; no `useEffect` + `fetch` for data loading.

## Cross-Browser & Responsive Requirements

All UI must work correctly on the latest two versions of: **Safari (macOS + iOS), Chrome, Edge, and Firefox**, across mobile, tablet, and desktop. Safari/iOS is the strictest target — if it works there, it usually works everywhere.

### Browser-engine gotchas to account for

- **Safari is the constraint, not Chrome.** Chrome (Blink) and Edge (Blink) behave nearly identically; Safari (WebKit) lags and differs most. Default to testing assumptions against WebKit behavior.
- **No flaky/experimental CSS.** Before using a feature, confirm Safari support. Provide fallbacks for anything not universally stable (e.g. `:has()` is fine now, but container queries, `subgrid`, and newer color functions need a fallback or graceful degradation).
- **100vh on mobile is broken in Safari** (it includes the URL bar, causing layout jump/overflow). Use `100dvh` (dynamic viewport height) with a `100vh` fallback, or `min-height: 100svh`.
- **iOS Safari auto-zooms on input focus** when font-size < 16px. Inputs/textareas/selects must use `font-size: 16px` (or larger) to prevent it.
- **Flexbox gap** is supported everywhere now, but verify on older Safari targets; if supporting Safari < 14.1, fall back to margins.
- **`backdrop-filter`** needs the `-webkit-` prefix for Safari.
- **Smooth scrolling / momentum**: add `-webkit-overflow-scrolling: touch` where relevant.
- **Date/number parsing**: never rely on `new Date("YYYY-MM-DD HH:mm")` — Safari rejects non-ISO formats and returns `Invalid Date`. Always parse via `date-fns` (`parseISO`) using the project's `src/utils/date.ts` helpers.
- **Avoid Chrome-only APIs** without feature-detection (e.g. `navigator.share`, `showOpenFilePicker`, certain `Intl` options). Feature-detect and degrade gracefully.
- **Event handling**: use Pointer Events (`onPointerDown` etc.) over mouse-only events so touch + mouse both work. `@dnd-kit` already handles this — prefer it over hand-rolled drag.
- **Passive scroll listeners**: don't block scrolling; let the dnd/scroll libraries manage this.

### Responsive requirements

- **Mobile-first.** Write base styles for small screens, then layer breakpoints upward with `min-width` media queries.
- **Standard breakpoints**: 640px (sm), 768px (md), 1024px (lg), 1280px (xl). Use these consistently.
- **No fixed pixel widths** for layout containers — use `%`, `fr`, `minmax()`, `clamp()`, and `max-width` instead. Fixed px is fine only for things like icons or borders.
- **Fluid typography**: prefer `clamp()` for font sizes that should scale (e.g. `clamp(1rem, 2.5vw, 1.25rem)`).
- **Tap targets**: interactive elements at least 44×44px on touch (Apple HIG minimum) so mobile users can tap reliably.
- **Test the three sizes**: every component must be checked/considered at ~375px (mobile), ~768px (tablet), and ≥1280px (desktop). State in your summary how the component behaves at each.
- **Overflow discipline**: long text, tables, and code must not break layout — use `overflow-x: auto`, `text-overflow: ellipsis`, `word-break`, or responsive table patterns (stack/scroll) as appropriate.
- **Images/media**: responsive by default (`max-width: 100%`, `height: auto`).

### Definition of done (additions)

- Component renders correctly at mobile / tablet / desktop widths.
- No use of browser-specific APIs without feature detection + fallback.
- No `100vh` on full-height mobile layouts (use `dvh`/`svh`).
- Inputs use ≥16px font-size to avoid iOS zoom.
- Any date handling goes through `src/utils/date.ts`, never raw `new Date(string)`.

## Testing Conventions

### Stack

- **Vitest** — test runner (config in `vitest.config.ts`, which extends `vite.config.ts`).
- **React Testing Library** + **@testing-library/user-event** — component tests.
- **@testing-library/jest-dom** — DOM assertions (`toBeInTheDocument`, etc.).
- **MSW (Mock Service Worker)** — mock the network layer for API-integration tests. Mock HTTP, never mock our own service functions.
- Shared test setup lives in `src/test/setup.ts`. Do not use Jest — this project is Vitest only.

### What to test (in priority order for this UI + API codebase)

1. **Pure functions** (`src/utils/`, services, formatters, validators, data mappers) — highest ROI, always test these.
2. **API integration** — with MSW, cover all four states for every data call: **loading, error, empty, success**. This is where most real bugs live; weight effort here.
3. **Custom hooks** with logic — test with `renderHook`.
4. **Component behavior** — test what the user sees and does, not markup.

### What NOT to test

- Static screens, layout, exact markup, or CSS classes — brittle and low value.
- Generated API code (`src/api/generated/`), third-party libraries, trivial getters.
- Implementation details (internal state, private functions). If a refactor that preserves behavior breaks the test, the test is wrong.

### How to write tests

- **Test behavior, not implementation.** Query by what the user perceives: role, label, text — not test IDs or class names (test IDs only as a last resort).
- **Use `user-event`, not `fireEvent`**, for interactions (clicks, typing) — it simulates real user behavior.
- **No filler assertions.** `expect(true).toBe(true)` or a render with no assertion is not a test. Every test must assert observable behavior.
- **One behavior per test.** Descriptive names: `it('shows an error when the API returns 500')`, not `it('works')`.
- **Colocate** test files next to source: `date.ts` → `date.test.ts` in the same folder. `src/test/` is for shared setup only.
- **Dates**: test through the helpers in `src/utils/date.ts`; never assert on raw `new Date()` output.

### Development flow (per ticket)

1. Build the component/function to satisfy the ticket.
2. Turn each **acceptance criterion into at least one test.** "Done" means every AC has a passing test. If a criterion can't be expressed as a test, the requirement isn't understood yet — flag it.
3. Run tests + fix until green before committing.
4. **Bug fixes start with a failing test** that reproduces the bug, then the fix makes it pass. This prevents silent regressions.

### Current phase note

The project is in static-UI development; APIs are not integrated yet. For now, write tests **only for pure logic** (utils, validators, formatters). Skip tests for static screens. Full component + MSW integration testing begins when API integration starts.

### Definition of done (testing additions)

- New pure functions in `src/utils/` or services have tests.
- Changed logic has a test proving the new behavior (bug fixes have a regression test).
- No implementation-detail assertions; no filler assertions.
- `npm run test:run` passes.

## MUI & Styling Conventions

This project uses **MUI (Material UI)** with a central theme as the single source of truth for design. The theme lives in `src/theme/theme.ts` and is provided via `ThemeProvider` + `CssBaseline` in `main.tsx`.

### Absolute rules

- **Never hardcode colors, spacing, radii, or font sizes** in components. No `sx={{ color: '#2563EB' }}`, no `padding: '16px'`. Use theme tokens:
  - Colors: `color="primary.main"`, `sx={{ bgcolor: 'background.paper', color: 'text.secondary' }}`
  - Spacing: `sx={{ p: 2, mt: 3, gap: 2 }}` (numbers = theme.spacing units, 1 = 8px)
  - Radii: inherit from theme, or `sx={{ borderRadius: 1 }}` (theme multiplier)
  - Typography: use `<Typography variant="h3">`, not manual font-size.
- If a value is needed repeatedly or is a design decision, it belongs in the **theme**, not scattered in `sx`. Add to `src/theme/theme.ts` (palette, typography, or component `styleOverrides`).
- **Layout with MUI components**: `Container`, `Box`, `Stack`, `Grid` — not raw divs with manual CSS. Reach for `Stack` for 1D layouts, `Grid` for 2D/responsive columns.

### Responsive

- Mobile-first, via MUI breakpoints `xs | sm | md | lg | xl`.
- Use responsive `sx` object syntax: `sx={{ py: { xs: 3, md: 5 } }}`.
- Use responsive `Grid` sizing: `<Grid size={{ xs: 12, sm: 6, md: 3 }} />`.
- **Grid import (MUI v6):** the Grid with the `size` prop is `import Grid from '@mui/material/Grid2'`. The plain `Grid` from `@mui/material` is the legacy API (uses `item`/`xs`/`md` props) — do not mix them.
- Every screen must be verified at mobile (~375px), tablet (~768px), desktop (≥1200px). State how it behaves at each in your summary.

### Building screens from the designers' code

The designers provide a reference implementation (their repo + live Vercel site). When building a screen:

1. Use their source as the source of truth for exact spacing, colors, and structure — translate those into **theme tokens**, don't copy hardcoded values.
2. If their styling method differs (Tailwind/CSS), translate to MUI `sx`/theme equivalents.
3. Rebuild in THIS project's structure (`src/pages/` or `src/features/`), themed and responsive — do not copy their file structure.
4. If a color/spacing value recurs and isn't in the theme yet, add it to the theme rather than inlining.

### Reference pattern

`src/pages/ExampleScreen.tsx` is the canonical example — copy its structure (Container → Stack header → Grid of Cards → themed form). New static screens should look structurally like it.

### Component reuse

- Prefer MUI components directly when the theme covers styling.
- When the design needs a consistent custom variant, set it via theme `components.styleOverrides` / `defaultProps`, OR create a wrapper in `src/components/common/`. Do NOT re-style the same component ad hoc on each screen.

### Definition of done (MUI additions)

- No hardcoded colors/spacing/radii/font-sizes; all via theme.
- Layout uses MUI layout components, not manual CSS divs.
- Responsive at xs/sm/md verified.
- Recurring design values live in `src/theme/theme.ts`, not inline.
